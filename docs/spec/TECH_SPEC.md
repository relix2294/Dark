# Техническая спецификация: Lablabu + Sor Box

Nov 22, 2026 · @Как Дела ?

Документ для команды разработки. Дополняет бизнес-ТЗ: там описано, что система делает, здесь — как она устроена.

## 1. Состав системы

Один бэкенд, два бренда (`LAB`, `SOR`), много точек. Бренд и точка — поля данных, а не отдельные инсталляции.

| Компонент | Назначение | Клиент |
| --- | --- | --- |
| `core-api` | Каталог, корзина, заказ, цены, промо, клиенты | REST + JSON |
| `payments` | Адаптер кошелька DC: холд, списание, возврат, сверка | Внутренний модуль, наружу не торчит |
| `wms` | Ячейки, остатки, приёмка, сборка, инвентаризация | Терминал сборщика (Android) |
| `kds` | Очередь кухни, станции, стоп-лист | Экран кухни (планшет, веб) |
| `dispatch` | Назначение курьеров, смены, геопозиция | Приложение курьера (Android) |
| `backoffice` | Админка: каталог, цены, промо, отчёты, роли | Веб |
| `storefront` | Витрина клиента внутри DC Next | Веб-окно или мини-приложение — решает банк |
| `notify` | Пуши, SMS, внутренние оповещения | Очередь сообщений |

**Архитектурные требования:**

- Модульный монолит с жёсткими границами модулей. Модули общаются через события и внутренние интерфейсы, не через чужие таблицы. На 4 точки микросервисы избыточны.
- Одна реляционная БД с транзакциями (рекомендация: PostgreSQL). Остатки и деньги меняются только в транзакции.
- Обновления в реальном времени (заказы, статусы, курьеры) — WebSocket или SSE; опрос допустим как запасной вариант.
- Все суммы — целые числа в дирамах (1 сомони = 100 дирам). Никаких `float` для денег и остатков.
- Все времена в UTC, отображение в `Asia/Dushanbe`.
- Каждый изменяющий запрос принимает `Idempotency-Key`; повтор с тем же ключом возвращает первый результат.
- Стек выбирает команда. Обязательны: типизированный API-контракт (OpenAPI), миграции БД в репозитории, тестовый контур, CI с автотестами сценариев приёмки.

- Товар с `is_high_value` лежит только в ячейке с `is_camera_covered`.
- `order.total = items_total + delivery_fee − discount`.

## 3. Машины состояний

Переход вне таблицы запрещён и возвращает `409 INVALID_TRANSITION`. Каждый переход пишется в `order_status_log` и порождает событие.

**Заказ**

| Из | В | Кто | Условие и действие |
| --- | --- | --- | --- |
| — | `created` | клиент | Корзина проверена: цены, остатки, зона, часы работы |
| `created` | `paid_hold` | система | Холд успешен. LAB: резерв остатков в той же транзакции |
| `created` | `payment_failed` | система | Холд отклонён или нет ответа 30 с. Резерв не создаётся |
| `paid_hold` | `picking` (LAB) / `cooking` (SOR) | сборщик / кухня | Задание взято в работу |
| `picking` / `cooking` | `ready` | сборщик / кухня | LAB: все позиции в статусе picked, replaced или missing. SOR: все блюда готовы и упакованы |
| `ready` | `on_the_way` | курьер | Курьер отсканировал пакет заказа |
| `on_the_way` | `delivered` | курьер | Подтверждение у двери. Запускается списание |
| `on_the_way` | `returning` | курьер | Клиент не вышел на связь: 2 звонка и ожидание по параметру `NO_SHOW_WAIT` |
| `returning` | `returned` | старший смены | Пакет принят на точке. LAB: товар возвращён в ячейки или списан |
| `paid_hold`, `picking`, `cooking`, `ready` | `cancelled` | клиент, оператор, система | Правила отмены — раздел 11. Холд снимается полностью или частично |

Клиент может отменить сам только до `picking` / `cooking`. Дальше — только оператор с причиной.

**Платёж**

`new → hold_pending → held → capture_pending → captured`

Ответвления: `hold_pending → failed`; `held → released` (отмена); `captured → refund_pending → refunded | partially_refunded`. Любое состояние `*_pending` старше 60 с попадает в задачу сверки (раздел 5).

**Задание курьера**

`offered → accepted → at_store → picked_up → delivering → done`

Ответвления: `offered → expired` (курьер не принял за `OFFER_TIMEOUT`, задание уходит следующему); `accepted → reassigned` (ручное вмешательство); `delivering → failed` (возврат на точку).

**Курьер**

`offline → free → assigned → delivering → returning → free`; из `free` доступен `break`. Статус `returning` выставляется автоматически после последней доставки в задании.

## 4. API-контракты

База: `/api/v1`. Формат JSON. Авторизация: клиент — токен сессии DC Next, обменянный на наш JWT; персонал — телефон и PIN, JWT с ролью и точкой. Полный OpenAPI-файл команда ведёт в репозитории; ниже обязательный минимум.

**Клиент (`storefront`)**

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/auth/dc` | Обмен токена DC Next на сессию. Тело: `dc_token` |
| GET | `/stores/resolve?lat&lon&brand` | Точка и зона по адресу: `store_id`, `fee`, `eta`, `is_open` |
| GET | `/catalog?store_id&brand&category&q` | Товары с ценой и признаком наличия. Остаток числом не отдаётся |
| PUT | `/cart` | Полная замена корзины. Ответ: пересчитанные суммы, применённое промо, недоступные позиции |
| POST | `/orders` | Создание заказа и холд. Требует `Idempotency-Key` |
| GET | `/orders/{id}` | Статус, состав, курьер (имя, позиция), `promised_at` |
| POST | `/orders/{id}/cancel` | Отмена клиентом |
| GET | `/orders/{id}/stream` | SSE: смена статуса, позиция курьера раз в 5 с |

Пример `POST /orders`:

```json
{
  "brand": "LAB",
  "store_id": "…",
  "address_id": "…",
  "items": [{"product_id": "…", "qty": 2, "replace_policy": "call"}],

  "comment": ""
```

## 5. Интеграция с кошельком DC

**Все деньги — только безналично и только через DC** (решение заказчика): оплата клиента, возвраты, выплаты курьерам. Наличных нет ни у клиента, ни у курьера. Lablabu и Sor Box работают как мини-приложения внутри экосистемы DC.

Контракт банка пока не получен. Модуль `payments` пишется за интерфейсом-адаптером; до получения API работает заглушка с теми же методами.

Кроме `hold / capture / release / refund / status`, адаптер умеет `payout` — выплату на кошелёк DC курьеру ([ADR-010](../adr/010-courier-payouts-dc.md)).

**Интерфейс адаптера**

| Метод | Вход | Выход |
| --- | --- | --- |
| `hold` | `dc_user_id`, `amount`, `order_number`, `idempotency_key` | `provider_ref`, `expires_at` или причина отказа |
| `capture` | `provider_ref`, `amount` (не больше холда), `idempotency_key` | результат |
| `release` | `provider_ref`, `idempotency_key` | результат |
| `refund` | `provider_ref`, `amount`, `idempotency_key` | результат |
| `status` | `provider_ref` | текущее состояние у банка |

**Последовательность оплаты**

1. `POST /orders`: в одной транзакции создаются `order` (`created`), `payment` (`hold_pending`), `payment_op` с ключом идемпотентности.
2. Вызов `hold` с таймаутом 10 с.
3. Успех: `payment = held`, `order = paid_hold`, резерв остатков. Отказ: `payment = failed`, `order = payment_failed`.
4. Таймаут: заказ остаётся в `created`, клиент видит «проверяем оплату». Задача сверки опрашивает `status` через 5, 15, 30 с. Нет ответа за 60 с — `release` и отказ.
5. Сумма холда — сумма заказа плюс `HOLD_BUFFER_PCT` (по умолчанию 10 %) для весового товара; для SOR буфер 0.
6. При `delivered` — `capture` на фактическую сумму: собранные позиции плюс доставка минус скидка. Остаток холда снимается.
7. Неуспешный `capture` повторяется с тем же ключом: 1, 5, 15 минут, затем раз в час в течение суток, после этого — тревога финансисту.

**Правила**

- Ключ идемпотентности операции: `{order_id}:{type}:{seq}`. Повторный вызов с тем же ключом не создаёт второго движения денег.
- Холд не должен истечь до доставки. За 10 минут до `hold_expires_at` при незавершённом заказе — тревога оператору.
- Возврат после списания — только через `refund`, с причиной и автором; сумма свыше `REFUND_LIMIT` требует роли управляющего.
- Ежедневная сверка в 04:00: реестр банка против `payment_op`. Расхождение — запись в отчёт «Деньги» и тревога.

**Что нужно получить от банка:** поддерживается ли частичное списание холда; срок жизни холда; есть ли идемпотентность на их стороне; вебхуки или только опрос; формат реестра для сверки; лимиты запросов.

## 6. Диспетчер курьеров

Самый сложный модуль: одни и те же курьеры возят два бренда с разным обещанием по времени. Диспетчер работает отдельно по каждой точке.

**Когда запускается:** заказ перешёл в `picking`; до готовности блюда SOR осталось `SOR_PREASSIGN` минут; курьер стал `free` или `returning`; задание истекло или отклонено; раз в 15 с по таймеру.

**Входные величины на заказ**

- `ready_eta` — прогноз готовности. LAB: старт сборки + `LAB_PICK_SLA`. SOR: максимум по блюдам от их `cook_time_sec` плюс очередь станции.
- `travel` — время в пути от точки до адреса: расстояние по дорогам, делённое на скорость транспорта курьера. На первом этапе допустимо расстояние по прямой × 1,4.
- `slack` = `promised_at` − сейчас − `travel`. Запас, который заказ может ждать.

**Алгоритм**

```text
function dispatch(store):
  lab = заказы LAB в picking|ready без курьера, по возрастанию created_at
  sor = заказы SOR без курьера, у которых ready_eta − now <= SOR_PREASSIGN,
        по возрастанию slack
  free = курьеры free + курьеры returning с eta_to_store <= RETURN_LOOKAHEAD

  # 1. Срочные SOR: запас исчерпан — выше любого нового LAB
  for o in sor where o.slack <= SOR_SLACK_BUFFER:
      assign(o, nearest(free))

  # 2. LAB в порядке очереди
  for o in lab:
      assign(o, nearest(free))

  # 3. Остальные SOR — только если остаётся резерв под LAB
  for o in sor (оставшиеся):
      if count(free) > LAB_RESERVE or нет активных корзин LAB за 5 минут:
          assign(o, nearest(free))
      else:
          ждать; заказ вернётся в шаг 1, когда slack упадёт до буфера

  # 4. Контроль ожидания
  for o in все ready без курьера:
      if wait(o) > NO_COURIER_WARN:  уведомить старшего смены
      if wait(o) > NO_COURIER_ALERT: тревога управляющему, предложить ручное назначение
```

`assign` создаёт `delivery_task` в статусе `offered`, шлёт пуш курьеру, ждёт `OFFER_TIMEOUT`. Курьер на точке в штате принимает автоматически — параметр `AUTO_ACCEPT`.

**Объединение поездок (этап 2)**

- Два заказа LAB в одну поездку: оба готовы с разницей не больше 2 минут, второй адрес добавляет к маршруту не больше `BATCH_DETOUR` минут, обещание первого не нарушается.
- LAB + SOR в одну поездку: только если LAB доставляется первым и SOR не теряет больше 5 минут.
- Не больше `BATCH_MAX` заказов на курьера.

**Ручное вмешательство:** старший смены может переназначить или снять заказ с курьера. Обязательны причина из списка и запись в журнал: кто, когда, что было, что стало.

**Что диспетчер пишет для разбора:** на каждое назначение — снимок входа (свободные курьеры, очередь, `slack` каждого заказа) и выбранное правило. Без этого спор «почему пицца ждала» не разобрать.

## 7. Склад Lablabu

**Адресное хранение.** Товар не привязан к постоянному месту: один товар может лежать в нескольких ячейках, в одной ячейке — разные товары. Система всегда знает, что где лежит, поэтому «вафли рядом с ручками» — норма, как в Ташкенте.

**Код ячейки:** `стеллаж-секция-полка`, например `A-03-2`. Штрихкод на каждой ячейке. У ячейки есть `pick_seq` — номер в маршруте обхода зала.

**Размещение (куда положить товар)**

1. Фильтр по температурной зоне товара.
2. Товар с `is_high_value` — только ячейки с `is_camera_covered`.
3. Запрет соседства похожих: в ячейке и в двух соседних не должно быть товара той же категории с похожим названием. Цель — исключить ошибку сборщика.
4. Ходовой товар (топ-20 % по частоте заказов) — в ячейки с меньшим `pick_seq`, ближе к зоне упаковки.
5. Из подходящих — ячейка с наибольшим свободным местом.

Система предлагает ячейку, кладовщик может выбрать другую допустимую. Недопустимую терминал не примет: `WRONG_CELL`.

**Резерв и списание остатка**

- Резерв при `paid_hold`: партии выбираются по ближайшему сроку годности (FEFO), `reserved_qty` растёт.
- Сборка: движение `pick`, `qty` и `reserved_qty` уменьшаются.
- Отмена или недобор: `unreserve`.
- Товар с остатком срока меньше `MIN_SHELF_LIFE_PCT` не резервируется и попадает в список на уценку или списание.

**Сборка**

1. Сборщик получает задание: позиции отсортированы по `pick_seq`.
2. На каждую позицию: скан ячейки → скан товара → количество. Несовпадение — ошибка со звуком, позиция не засчитывается.
3. Весовой товар: ввод фактического веса, сумма позиции пересчитывается.
4. Товара нет: по `replace_policy` заказа — `call` (звонок клиенту, таймер 60 с), `auto` (замена из списка аналогов не дороже), `remove` (убрать и вернуть деньги).
5. Конец сборки: печать ярлыка пакета с номером заказа и штрихкодом, пакет ставится в зону выдачи по температурной зоне.

Норматив: 2 минуты на заказ в среднем. Терминал показывает сборщику таймер; время по каждому заказу и сборщику идёт в отчёт.

**Приёмка:** по документу поставки, скан товара, количество, срок годности. Расхождение с документом фиксируется актом. Товар без штрихкода получает внутренний, печать на месте.

**Инвентаризация:** ежедневно выборочно — ячейки, где за день был недобор при сборке, и все ячейки с дорогим товаром; раз в неделю — полный круг по графику. Расхождение выше `STOCKTAKE_TOLERANCE` требует повторного пересчёта другим сотрудником.

**Работа без связи:** терминал хранит текущее задание и принимает сканы локально до 30 минут, затем отправляет очередь на сервер. Новые задания без связи не выдаются.

## 8. Кухня Sor Box

**Станции:** `pizza`, `grill`, `cold`, `pack`. У каждой свой экран или вкладка. Состав станций настраивается по точке.

**Раскладка заказа.** Заказ делится на блюда, каждое уходит на свою станцию. Чтобы всё было готово одновременно, блюдо стартует не сразу, а в момент:

`старт блюда = целевая готовность заказа − cook_time блюда`

Целевая готовность заказа = сейчас + самое долгое блюдо + очередь его станции. Экран показывает блюдо серым до времени старта, затем жёлтым, красным — при опоздании.

**Очередь станции:** сортировка по времени старта. Вместимость станции (`STATION_CAPACITY`, например 4 пиццы в печи) ограничивает число блюд в работе; из неё считается задержка для новых заказов.

**Обещание клиенту.** `promised_at` = готовность + ожидание курьера + путь. Если расчёт превышает `SOR_MAX_PROMISE` (по умолчанию 60 минут), витрина показывает увеличенное время до оформления заказа, а не после.

**Упаковка:** станция `pack` видит заказ целиком, отмечает каждое блюдо, печатает ярлык. Только после этого заказ получает статус `ready`.

**Стоп-лист:** кухня отключает блюдо или ингредиент. Блюда с этим ингредиентом исчезают с витрины в течение 10 с. Стоп-лист сбрасывается при открытии смены, с подтверждением.

**Списание ингредиентов:** по рецептуре при статусе `ready`. На первом этапе — учёт расхода без резерва; остатки кухни сверяются ежедневной инвентаризацией. Полный складской учёт кухни — этап 2.

**Блюда Sor Box в заказе Lablabu (этап 2):** позиция уходит в очередь кухни как обычное блюдо, сборщик забирает её со станции `pack` перед закрытием сборки.

## 10. События, уведомления, мониторинг

**События.** Каждое изменение состояния публикует событие в той же транзакции (таблица `outbox`), отдельный процесс доставляет его подписчикам. Так событие не теряется при сбое.

Обязательный набор: `order.created`, `order.status_changed`, `order.item_replaced`, `payment.held`, `payment.captured`, `payment.failed`, `payment.refunded`, `stock.low`, `stock.out`, `task.offered`, `task.accepted`, `task.expired`, `courier.status_changed`, `kds.item_late`, `dispatch.no_courier`.

**Уведомления клиенту**

| Момент | Канал | Текст (смысл) |
| --- | --- | --- |
| Заказ принят | пуш | Номер заказа и время доставки |
| Замена или нет товара | пуш + экран заказа | Что заменено, новая сумма |
| Курьер выехал | пуш | Имя курьера, ссылка на карту |
| Задержка больше 5 минут от обещания | пуш | Новое время, извинение |
| Доставлен | пуш | Списанная сумма, ссылка на чек, оценка |
| Отмена, возврат | пуш | Причина и сумма возврата |

Если пуш через DC Next не доставлен за 30 с — SMS для событий «курьер выехал» и «отмена».

**Журнал действий.** Неизменяемая запись: кто, когда, действие, объект, было, стало, причина. Обязательно для: изменения цены, корректировки остатка, списания, возврата денег, отмены заказа, ручного назначения курьера, изменения промо, ролей и параметров. Хранение — 3 года.

**Мониторинг и тревоги**

| Метрика | Порог тревоги | Кому |
| --- | --- | --- |
| Доля ошибок API | больше 2 % за 5 минут | дежурный разработчик |
| Время ответа `POST /orders`, 95-й перцентиль | больше 2 с | дежурный разработчик |
| Неуспешные холды | больше 10 % за 10 минут | дежурный + банк |
| Платежи в `*_pending` дольше 5 минут | любой | финансист |
| Заказ `ready` без курьера | `NO_COURIER_ALERT` | управляющий точки |
| Терминал или экран кухни не на связи | 2 минуты в рабочее время | старший смены |
| Очередь `outbox` | больше 100 событий или старше 1 минуты | дежурный разработчик |

Логи структурированные, с `request_id` и `order_id`. В логи не попадают токены, полные номера телефонов и данные кошелька.

## 11. Крайние случаи

| Ситуация | Поведение системы |
| --- | --- |
| Два клиента покупают последнюю единицу | Резерв в транзакции с блокировкой строки партии. Второй получает `OUT_OF_STOCK` до холда, деньги не трогаются |
| Двойное нажатие «Оплатить» | Один `Idempotency-Key` на корзину — один заказ и один холд |
| Холд прошёл, ответ банка потерян | Сверка через `status`; заказ продолжается или холд снимается. Клиент не платит дважды |
| Цена изменилась, пока товар в корзине | `PRICE_CHANGED`, клиент подтверждает новую сумму |
| Товара нет на полке, в системе есть | Сборщик жмёт «нет»: замена по правилу заказа, остаток ячейки обнуляется до пересчёта, ячейка попадает в инвентаризацию дня |
| Клиент не отвечает на звонок о замене | Через 60 с позиция убирается, сборка продолжается |
| После недобора сумма ниже минимальной | Заказ доставляется, минимум проверяется только при оформлении |
| Отмена клиентом до начала сборки или готовки | Полное снятие холда, резерв снят |
| Отмена SOR после начала готовки | Только оператор. Списывается стоимость приготовленного — по параметру `SOR_CANCEL_FEE_PCT`; блюда идут в списание с причиной |
| Курьер потерял связь в пути | Приложение копит события с метками времени и отправляет при восстановлении. Сервер принимает их по времени события, а не получения |
| Курьер жмёт «доставлено» далеко от адреса | Дальше `DELIVERY_GEOFENCE` метров — `TOO_FAR_FROM_ADDRESS`; подтвердить может только старший смены с причиной |
| Клиент не открыл дверь | 2 звонка, ожидание `NO_SHOW_WAIT`, возврат на точку. LAB: товар на полку, кроме охлаждённого и замороженного — они в списание. Доставка списывается, товар — нет. SOR: списывается полная сумма |
| Точка закрывается, есть незавершённые заказы | Приём заказов останавливается за `LAST_ORDER_BEFORE_CLOSE` минут; смену нельзя закрыть, пока есть активные заказы |
| Промо новичка используют повторно | Проверка по `dc_user_id` и по адресу: не больше `per_customer_limit` на клиента и не больше 2 новичков на один адрес |
| Бюджет промо исчерпан | Промо отключается атомарно при достижении `budget_dirams`, перерасход невозможен |
| Сервер недоступен | Витрина показывает «временно не принимаем заказы». Терминал, кухня и курьер дорабатывают уже полученные задания из локальной копии |
