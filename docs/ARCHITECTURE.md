# Архитектура

Документ отвечает на вопрос «как устроено», ТЗ — на вопрос «что делает». Ссылки вида «ТЗ §N» ведут в [spec/TECH_SPEC.md](spec/TECH_SPEC.md).

## 1. Форма системы: модульный монолит

Один процесс `apps/api`, внутри — модули с жёсткими границами (ТЗ §1). На 4 точки микросервисы избыточны:
они дают сетевые отказы и распределённые транзакции там, где достаточно одной БД.

```
apps/api/src
├── app.ts            сборка Fastify: плагины, обработчик ошибок, регистрация модулей
├── server.ts         точка входа: конфиг → приложение → воркеры
├── workers.ts        фоновые задачи (pg-boss)
├── config.ts         переменные окружения через zod
├── shared/           общее для всех модулей; НЕ импортирует modules/
│   ├── db/           клиент Drizzle, схема (schema/*.ts), migrate.ts, seed.ts
│   ├── errors/       AppError → {"error": {code, message, details}}
│   ├── events/       outbox: publish() в транзакции + OutboxRelay
│   ├── auth/         PIN (scrypt), JWT (jose), матрица прав, плагин Bearer
│   ├── idempotency/  плагин Idempotency-Key
│   ├── params/       настраиваемые параметры (ТЗ §12) и их значения по умолчанию
│   ├── money.ts      дирамы: целые, округление, формулы холда и итога
│   ├── geo.ts        haversine, точка-в-полигоне, время в пути
│   └── state-machine.ts  таблица переходов → 409 INVALID_TRANSITION
└── modules/
    ├── catalog/      точки, зоны, товары, цены, блюда; часы работы
    ├── customers/    клиент (DC Next) и персонал: вход, токены
    ├── orders/       корзина, заказ, переходы статусов, SSE
    ├── promo/        промокоды, атомарный бюджет
    ├── payments/     адаптер кошелька DC (интерфейс + заглушка), машина состояний платежа
    ├── wms/          ячейки, партии, размещение, FEFO-резерв, сборка
    ├── kds/          очередь станций, раскладка блюд, стоп-лист
    ├── dispatch/     курьеры, задания, планировщик назначений
    ├── notify/       подписчики outbox → пуши / SMS
    └── backoffice/   параметры, журнал действий, отчёты, персонал
```

**Правила границ** (проверяет `scripts/check-boundaries.mjs`, запускается в `pnpm lint` и в CI):

1. Модуль импортирует из другого модуля только его `index.ts` — публичный интерфейс. Внутренние файлы чужого модуля недоступны.
2. `shared/` не знает о модулях.
3. У каждой таблицы один владелец (список `OWNERSHIP` в скрипте). Писать в чужую таблицу нельзя; читать — можно через функции владельца.
   Пример: `orders` не трогает `stock_lot` напрямую, а зовёт `wms.planReserve` и делает движения `stock_move` в своей транзакции
   только потому, что резерв — часть сценария заказа (ТЗ §3). Это осознанное исключение, зафиксированное в коде комментарием.

Внутри модуля файлы по ролям: `index.ts` (интерфейс + маршруты), `service.ts` (сценарии, транзакции), чистые функции
(`planner.ts`, `schedule.ts`, `placement.ts`, `reserve.ts`, `pricing.ts`) — без БД, покрыты unit-тестами.

## 2. Данные

- **PostgreSQL 16**, одна БД, схема в `shared/db/schema/*.ts` (Drizzle), миграции SQL в `apps/api/drizzle/`.
  `drizzle-kit generate` создаёт миграцию из схемы; руками пишутся только инварианты и служебные объекты (`0001_invariants.sql`).
  CI проверяет, что схема и миграции не расходятся.
- **Деньги** — целые дирамы (`integer`). **Остатки** — целые единицы (для весового товара — граммы). Float запрещён на уровне типов (`shared/money.ts`).
- **Время** — `timestamptz` (UTC), отображение в `Asia/Dushanbe` на клиенте.
- **Enum-ы** объявлены один раз в `@dark/contracts` как кортежи `*_VALUES`; из них собираются и zod-схемы, и `pgEnum`.
- **Инварианты в БД** (ТЗ §2): CHECK на `stock_lot` (qty ≥ reserved ≥ 0), `payment` (captured ≤ hold, refunded ≤ captured),
  `order` (total = items + fee − discount); триггер «дорогой товар только в ячейку с камерой»; `audit_log`, `order_status_log`,
  `stock_move` — только добавление (триггер запрещает UPDATE/DELETE).
- **Остаток = сумма движений**: любое изменение `stock_lot.qty/reserved_qty` сопровождается строкой `stock_move` в той же транзакции.
- **Гео без PostGIS**: точка и адрес — `lat/lon`, зона — полигон GeoJSON в `jsonb`, проверка в коде. На 4 точки и десятки зон этого достаточно; PostGIS — ADR-005 на вырост.

## 3. Сценарий заказа (ТЗ §4, §5, §11)

```
POST /orders  (Idempotency-Key)
 ├─ tx1: пересчёт корзины → PRICE_CHANGED / OUT_OF_STOCK / STORE_CLOSED / MIN_ORDER
 │       order(created) + order_item + резерв FEFO с FOR UPDATE по партиям (LAB)
 │       + payment(hold_pending) + payment_op(key = {order}:hold:1) + outbox(order.created)
 ├─ wallet.hold()  — вне транзакции БД, таймаут PAYMENT_HOLD_TIMEOUT_MS
 └─ tx2: ok      → payment(held), order(paid_hold), outbox(payment.held, order.status_changed)
         declined→ payment(failed), unreserve, order(payment_failed) → 402 PAYMENT_DECLINED
         timeout → заказ остаётся created, резерв держится; сверка опрашивает status() (воркер payments.reconcile)
```

Два покупателя последней единицы: резерв в tx1 блокирует строки партий (`SELECT … FOR UPDATE`), второй получает `OUT_OF_STOCK`
до вызова банка — деньги не трогаются (ТЗ §11). Если банк отказал, резерв снимается в tx2.

## 4. Идемпотентность (ТЗ §1)

Плагин `shared/idempotency` на хуке `preValidation`: все `POST/PUT/PATCH/DELETE` требуют `Idempotency-Key` (кроме маршрутов с
`config.idempotency = false` — вход, телеметрия позиции). Ключ хранится в `idempotency_key` в рамках субъекта (клиент или сотрудник)
вместе с хэшем запроса и ответом. Повтор → тот же ответ с заголовком `idempotent-replayed: true`; тот же ключ с другим телом →
`409 IDEMPOTENCY_CONFLICT`; 5xx не фиксируется, клиент может повторить.

Операции с банком идемпотентны отдельно: `payment_op.idempotency_key = {order_id}:{type}:{seq}` (уникальный индекс).

## 5. События и фон (ТЗ §10)

- **Outbox**: `publish(tx, event)` пишет строку в `outbox` в той же транзакции, что и изменение. `OutboxRelay.tick()` берёт
  неопубликованные пачкой с `FOR UPDATE SKIP LOCKED` (можно несколько инстансов), доставляет подписчикам, отмечает `published_at`,
  при ошибке увеличивает `attempts`.
- **pg-boss** (очередь в Postgres, схема `pgboss`): `outbox.relay` (каждые 2 с), `dispatch.tick` (15 с), `payments.reconcile` (1 мин),
  `housekeeping` (03:00). Redis не нужен.
- **Подписчики** живут в `modules/notify` — модули-источники не знают о пушах и SMS.
- Мониторинг очереди outbox (ТЗ §10: > 100 событий или старше 1 мин) — метрика для следующей итерации.

## 6. Realtime

- Клиент: SSE `GET /orders/{id}/stream` — статус и позиция курьера раз в 5 с. Этап 1 — опрос БД внутри сервера; этап 2 — подписка на outbox.
- Экраны персонала (пульт, кухня, терминал): WebSocket (`@fastify/websocket`), события из outbox по точке. Подключается вместе с маршрутами модулей.

## 7. Авторизация (ТЗ §4, §9)

- Клиент: `POST /auth/dc` — обмен токена DC Next на наш JWT (`kind: customer`). Проверка токена банка — за адаптером, пока заглушка `dc:<id>` вне production.
- Персонал: `POST /auth/staff` — телефон + PIN (scrypt), JWT с ролью и точкой (`kind: staff`).
- Права: `PERMISSIONS` в `shared/auth` — действие → роли, один в один с матрицей ТЗ §9. `requireStaff(principal, 'wms.pick', storeId)`
  проверяет роль и принадлежность точке. Сотрудник видит только свою точку; `admin` и `finance` без привязки.

## 8. Клиенты

| Приложение | Технология | Почему |
| --- | --- | --- |
| Витрина (`apps/storefront`) | React + Vite, PWA | Открывается внутри DC Next как веб-окно; формат уточняется с банком |
| Админка и пульт (`apps/backoffice`) | React + Vite | Таблицы, карта курьеров, отчёты |
| Кухня (`apps/kds`) | React + Vite, планшет | Крупные элементы, WebSocket-очередь, работа одной рукой |
| Терминал сборщика (`apps/picker`) | React PWA на Android-терминале | Аппаратный сканер отдаёт штрихкод как клавиатуру — PWA хватает; оффлайн-очередь сканов до 30 мин в IndexedDB (ТЗ §7) |
| Курьер (`apps/courier`) | Expo (React Native) | Фоновая геопозиция раз в 5 с и пуши — только нативно |

Все клиенты используют `@dark/contracts` для типов и генерируемый из OpenAPI клиент. Макеты — этап 0 (ТЗ §9).

## 9. Эксплуатация

- **Один VPS** (как у Kassa): `deploy/docker-compose.yml` — Postgres, миграции (отдельный one-shot сервис), API, Caddy с TLS.
  Статика фронтов — в `deploy/www/<app>` за Caddy. Когда появится вторая точка нагрузки — вынести Postgres в managed (Neon/Supabase), API остаётся без изменений.
- **CI**: типы, границы модулей, миграции с нуля, тесты против Postgres, проверка расхождения схемы; на `main` — образ в GHCR.
- **Логи**: pino, JSON, `request_id` на каждый запрос, редактирование токенов/телефонов/ответов банка (ТЗ §10).
- **Конфигурация**: только переменные окружения (`config.ts`, zod). Бизнес-параметры (ТЗ §12) — в таблице `parameter` по точке, меняются из админки.

## 10. Тестирование

- Unit: чистые функции (деньги, гео, машины состояний, диспетчер, раскладка кухни, размещение, FEFO, промо, корзина).
- Интеграция: `test/orders.test.ts` поднимает приложение против `TEST_DATABASE_URL`, применяет миграции и прогоняет сценарии приёмки ТЗ §11
  (PRICE_CHANGED, последняя единица, отказ банка, отмена, идемпотентность, права).
- Правило: каждая строка таблицы крайних случаев ТЗ §11 получает тест в момент реализации.
